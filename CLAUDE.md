## Архитектура
- Хостинг: публичный репозиторий GitHub + GitHub Pages (публикация своим workflow — нет лимита 10 сборок/час).
- «Сервер» = GitHub Actions: сборщик на Python (`collector/`, только стандартная библиотека) скачивает данные, приводит к единому формату, сохраняет JSON и картинки в `site/data/` и `site/img/`. Браузер к источникам не ходит.
- Каждый набор данных — файл-«конверт»: `source`, `fetchedAt` (последний успех), `checkedAt` (последняя попытка), `status` (`ok`/`stale`/`error`), `error`, `data`. Источник не ответил → остаются прошлые данные со старым `fetchedAt` и статус `stale`.
- Сохранённые данные — в ветке `data` (одна перезаписываемая версия: `commit --amend` + force-push) → переживают любые перезапуски. В `main` данных нет (`site/data/`, `site/img/` в .gitignore).
- Workflows (`.github/workflows/`):
  - `collect.yml` — **дежурство**. Cron `2-59/5 * * * *` GitHub на деле запускал ~раз в час (11.11.2026: 09:16, 10:15, 11:14, 12:05, 13:06, 14:20 UTC), поэтому каждый запуск работает непрерывно: восстанавливает данные из ветки `data` (`scripts/ci_restore_data.sh`), затем `python3 -m collector loop` — раз в 60 с проход (качается только то, что пора по частотам ниже; «пустой» проход ничего не скачивает) и `scripts/ci_publish.sh`, если изменился отпечаток.
    - Передача смены: после каждого прохода `scripts/ci_newer_run.sh` смотрит, ждёт ли в очереди следующий запуск `collect.yml` (группа concurrency `collect`, по одному). Ждёт → текущий выходит, новый стартует через ~30–60 с и продолжает с данными из ветки `data`. Так подхватывается и новый код.
    - Предел дежурства 320 мин (задача GitHub — до 6 ч); если к этому времени смены в очереди нет — запуск сам ставит следующий (`gh workflow run collect.yml`). 5 падений сборщика подряд → выход с ошибкой, без самоперезапуска (поднимет следующий cron).
    - После пуша нового кода сборщика: `gh workflow run collect.yml -R ijpteb/gsw-portal` — текущая смена уступит место запуску с новым кодом в течение минуты. Ручной запуск с `-f force=true` — то же + «обновить всё» в первом проходе.
  - `ci_publish.sh` запускает `deploy.yml` через `gh workflow run`, если изменился `site/data/fingerprint.txt` (отпечаток всего, кроме `checkedAt`; меняется при каждом успешном получении данных). Пуши через GITHUB_TOKEN не запускают другие workflow — поэтому workflow_dispatch. Что уже опубликовано в этом запуске — файл `.published-fp` (пишется последним: сорвался push/запуск публикации → следующий вызов повторит).
  - `deploy.yml` — Pages: код из main + данные из ветки `data`; при пуше в main тоже. `cancel-in-progress: false` (иначе частые live-публикации отменяли бы друг друга). Подставляет версию кода в адреса JS/CSS (см. «Фронтенд»).
  - `tests.yml` — автотесты; `keepalive.yml` — еженедельный коммит в main (против отключения cron через 60 дней); `probe.yml` — ручная проверка источников с серверов GitHub (результаты и ответы — артефакт `probe-responses`).
- Замеры на GitHub (11.11.2026): сбор ~27 с, публикация ~21 с; от запуска сбора до обновлённых данных на сайте — 44 с. Pages отдаёт `cache-control: max-age=600`, CDN сбрасывается при публикации → страницы должны запрашивать JSON с `fetch(url, {cache: 'no-cache'})` (иначе браузер держит старое до 10 мин).
- Особенность CDN Pages: если файл запросили ДО его первой публикации, ответ 404 может держаться в кэше долго (11.11.2026 новый репозиторий: 18 мин). Касается только новых файлов (например, `gamelog/<id>.json` нового игрока) — страницы должны спокойно показывать «нет данных», а не ломаться.
- Частота: матч — раз в 60 с; день матча (за 12 ч до начала и 5 ч после) — расписание раз в 5 мин; таблица, статистика, состав, травмы, журналы матчей — раз в час; новости — 20 мин; логотипы — неделя. После неудачи — повтор не чаще раза в 10 мин. Сразу после конца матча — внеочередное обновление расписания, таблицы и статистики.
- Проверка сбоя источников: `GSW_BLOCK_HOSTS=espn python3 -m collector run --force` (можно несколько через запятую).
- Работа с каждым источником — в одном файле `collector/sources/<источник>.py`. На каждый — настоящий сохранённый ответ в `tests/fixtures/` и автотесты.
- Фронтенд: обычные HTML/CSS/JS-модули в `site/`, без сборки и внешних библиотек; шрифты системные (ничего не скачиваем).
  - `index.html` — каркас: шапка (лупа, избранное, «Обновить»), меню разделов (компьютер ≥1120 px), нижняя панель + окно «Ещё» (телефон, планшет), окно поиска. `css/app.css` — всё оформление; цвета — переменные в `:root` (фон `#08122b`, золото `#ffc72c`); «уменьшить движение» отключает анимации.
  - `js/app.js` — переходы по адресам `#/…`, меню, «Обновить», проверка свежих данных раз в минуту (во время матча — раз в 30 с): изменился `status.json → generatedAt` → перечитываются загруженные наборы и перерисовывается страница.
  - `js/data.js` — загрузка конвертов (`fetch(..., {cache: 'no-cache'})`; нет файла/сети → `{missing, dataset, error}`; без сети остаётся прежняя версия). `js/ui.js` — `h()` (элементы только с текстом, без innerHTML для данных), иконки, `sourceLine()` (источник и время; каких данных нет и почему; «показаны данные от …»), `noData()`, заглушки фото (номер + инициалы). `js/format.js` — даты/числа по-русски, пояс устройства. `js/games.js` — последний/следующий/идущий матч. `js/favorites.js` — избранное в `localStorage`: `gsw.favorites.v1` (id ESPN), `gsw.favorites.names.v1` (имена — чтобы ушедший игрок не стал безымянным). `js/search.js` — поиск по фамилии (латиницей, как у ESPN) и номеру. `js/sections.js` — список разделов: из него строятся все меню; `stage` — на каком этапе появится. `js/pages/*.js` — страницы.
  - Адреса: `#/` главная; `#/player/<id>` (пока коротко — полная карточка на этапе 3); `#/news/<id>`; `#/favorites`; `#/status` — служебная «Состояние данных»; остальные разделы — заглушки «в разработке · этап N».
  - Версия кода: в исходниках все импорты и файлы — с `?v=__V__`, `deploy.yml` подставляет 8 знаков коммита. Иначе после обновления браузеры до 10 мин смешивали бы старые и новые файлы. Новый импорт — обязательно с `?v=__V__` (проверяет `tests/test_site.py`).
- Факты GitHub (docs, 11.11.2026): cron не чаще раза в 5 мин и может опаздывать (особенно в начале часа); в публичном репо расписание отключается после 60 дней без активности; Actions бесплатны для публичных репо; задача — до 6 ч.

## Как запускать (локально)
- Сбор данных: `python3 -m collector run` (из папки проекта); всё сейчас: `--force`; состояние: `python3 -m collector status`.
- Дежурство как на GitHub: `python3 -m collector loop [--tick 60] [--max-minutes N] [--after-update CMD] [--handover CMD]` (выход, когда `--handover` вернёт код 0).
- Тесты: `python3 -m unittest discover -s tests -t .` (45 тестов, на настоящих ответах; дежурство — `tests/test_loop.py`, код сайта — `tests/test_site.py`).
- Источники вживую: `python3 tests/check_sources.py` (`--save` → `tests/fixtures/new/`); запасные: `python3 tests/probe_backup_sources.py`.
- GitHub CLI: `~/.local/bin/gh` (вход ijpteb, права repo+workflow). Ручной сбор на GitHub: `gh workflow run collect.yml -R ijpteb/gsw-portal -f force=true`.
- Python с python.org на Mac не видит сертификаты — `collector/http.py` подключает `/etc/ssl/cert.pem` сам.
- Просмотр сайта локально: `python3 scripts/dev_server.py` → http://localhost:8765 (отдаёт `site/` без кэша; данные — из локального `site/data/` после `python3 -m collector run`, локально он идёт ~3 мин — ESPN отвечает медленнее, чем GitHub). Для владельца — двойной щелчок по `Запустить сайт.command` (скачает данные и откроет браузер). В Claude: `.claude/launch.json` → сервер «site». Встроенная панель браузера, пока скрыта, отдаёт устаревшие снимки экрана — проверять текст и размеры через JS.
